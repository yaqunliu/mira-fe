# mira-fe Docker 部署设计

## 目标

把 `mira-fe` 从当前的普通 Node.js 进程启动方式，改成可以直接在服务器上用 Docker 启动的前端服务。

这次只处理前端仓库，不改已经在线运行的后端服务。前端容器启动后，需要满足下面两件事：

- 前端服务能在服务器端口上稳定启动
- 前端请求后端时，直接访问正式后端域名 `https://api-creator.mira-studio.ai`

## 约束

- 不把后端服务纳入当前前端仓库的 `docker-compose.yml`
- 不依赖容器内网地址访问后端
- 保留当前前端默认生产端口 `8001`
- 尽量少改业务代码，重点放在部署文件和运行配置

## 方案

### 1. 使用多阶段 Docker 构建

前端是 `Next.js` 项目，最稳妥的做法是：

- 第一阶段安装依赖
- 第二阶段执行生产构建
- 第三阶段只复制运行所需文件，生成更小的运行镜像

这样做的好处是镜像更小，也更适合服务器长期运行。

### 2. 使用 Next.js standalone 产物

为了让运行镜像不需要完整源码和完整依赖目录，需要把 `Next.js` 输出切换为 `standalone`。

这样容器内只需要：

- `server.js`
- `.next/static`
- `public`

就可以启动前端服务。

### 3. Docker Compose 只负责前端容器

前端仓库新增自己的 `docker-compose.yml`，用于：

- 构建前端镜像
- 映射端口 `8001:8001`
- 注入生产环境变量
- 设置自动重启

这样服务器上只需要执行一条命令就能启动前端。

### 4. 后端访问改为正式域名

前端容器内统一使用：

- `NEXT_PUBLIC_API_URL=https://api-creator.mira-studio.ai`

这样浏览器和前端服务都会直接请求正式后端域名，不再依赖本地 `BACKEND_URL` 或容器网络。

## 文件范围

- 新增 `Dockerfile`
- 新增 `docker-compose.yml`
- 新增前端容器环境变量示例文件
- 修改 `next.config.js`，让构建产物适配 Docker 运行
- 更新 `README.md`，补充前端 Docker 启动方式

## 风险和处理

### 风险 1：前端构建时拿不到正式接口地址

因为 `NEXT_PUBLIC_API_URL` 会影响浏览器端代码，所以构建镜像时就要把这个值传进去。

处理方式：

- 在 `Dockerfile` 里增加构建参数
- 在 `docker-compose.yml` 里同时传构建参数和运行时环境变量

### 风险 2：沿用现在的 `next start` 方式会让镜像偏大

处理方式：

- 使用 `standalone` 输出
- 只复制运行时需要的文件到最终镜像

### 风险 3：说明文档和实际部署方式不一致

处理方式：

- 在 `README.md` 里新增明确的 Docker 启动步骤
- 给出最小可执行命令，避免继续沿用旧的 PM2 说明
